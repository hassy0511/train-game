## 1. 単位・ゲージ・車両寸法（提案）

| 項目 | 値 | 理由 |
|---|---|---|
| 単位・座標系 | 1 unit = 1 m、Y が上、右手系。モデルの前方は +Z | Three.js / glTF の標準 |
| 線路ゲージ（レール中心間） | **1.5 m** | 切りのよい値。実在規格（1.067 / 1.435）と一致させない |
| レール断面 | 幅 0.10 m × 高さ 0.15 m | |
| 枕木 | 2.4 × 0.25 × 0.15 m、間隔 0.8 m | |
| バラスト（盛土） | 上面幅 3.2 m、底面幅 4.4 m、高さ 0.3 m | 線路が地面から少し盛り上がって見える |
| 線路の高さ基準 | ステージJSONの線路の点は **レール上面の高さ** で書く。地面は −0.6 m | 電車の原点がそのままレールに乗る |
| 車両 | **長さ 12.0 × 幅 3.0 × 高さ 3.6 m**、1両編成 | 幅がゲージの2倍のずんぐり体型。実在車両より短くして急カーブで遊べる |
| 台車 | 車体中心から前後 ±4.0 m | 車体の向きは前後台車の位置から決める（カーブで自然に曲がる） |
| 車体の原点 | 車体中心の真下、レール上面の高さ、前方 +Z | 線路上の点 = 原点 |
| 運転席カメラ | 原点から (0, 2.6, 5.0)。前方向き。垂直画角 60° | 窓枠とダッシュボードが下に少し見える高さ |
| 相棒の席（Phase 1） | 原点から (+0.9, 1.6, 5.0) | 画面右端に見える |
| 最小カーブ半径（制作の目安） | 40 m | これ以下だと車体が線路からはみ出して見える |
| 最大勾配（制作の目安） | 15 %（0-0 は 6 %） | 架空なので急でよい |

| 段 | 表示 | 速度 |
|---|---|---|
| 0 | とまる | 0 m/s |
| 1 | ゆっくり | 5 m/s（18 km/h） |
| 2 | ふつう | 12 m/s（43 km/h） |

## 3. ステージJSONスキーマ v1（提案）

詳細は **`docs/STAGE_SCHEMA.md`**（フィールド定義と 0-0 の実例）。ここでは方針だけ。

- 1ステージ1ファイル `src/stages/<chapter>-<n>.json`。`schemaVersion: 1` を持つ
- 線路上の位置は **始点からの距離（m）`at`** で書く。内部では TECH_SPEC の通りスプラインの `t` に変換する
  - 理由: 人も Codex も「120 m 地点に分岐」と書けるが、`t=0.283` は書けない
- 分岐: `railId` と `at` と、左右それぞれの行き先 `railId`。行き先が今の線路なら分岐しない。無操作時は `default`
  - 分岐先の線路の始点は分岐点と一致させる（ローダーが 0.5 m 以内かを検証）。接線はローダーが自動でそろえる
- 線路の終わり方 `end`: `buffer`（車止め・自動停止）／`merge`（他の線路に合流）／`open`（何もない。Phase 2 の落下用）
- 配置物・アクター・記録の位置は「世界座標」か「線路上（`railId` + `at` + 横オフセット）」のどちらでも書ける。線路上指定は木や岩を並べるのに楽
- ステージ解放条件 `unlock.requires`（クリア済みステージID）と課金フラグ `unlock.purchase` をデータ側に持つ
- ローダーの検証: 必須フィールド、`railId` 参照、分岐点の一致、`at` が線路長の範囲内、モデル名の形式

## 6. 仮ステージ 0-0「てすとこーす」

線路は Y 字。始点から 120 m 直進 → 分岐。**左**（無操作時）は半径 60 m で左に曲がり、6 % の上り下りの丘を越えて車止め。**右**は半径 60 m で右に曲がって平地を走り車止め。

```
                 ←── branch（右）        main（左）──→
   車止め ──────(-60,180)             (60,180)──── 丘 ────── 車止め
                      ＼               ／
                       ＼   分岐     ／
                        ＼ (0,120) ／
                             │
                             │  直進 120 m（25 m 地点にセンサー）
                             │
                        (0,0) 始点「はじまりえき」
```

- 線路長: main 約 424 m、branch 約 214 m
- センサー 1 個: main の 25 m 地点（発車 5 秒以内に通過する）。通過で `sensor-1 enter / exit` をログ
- 配置物: 木 2 種 26 本、岩 6 個を線路脇に。Y の内側にも数本
- 終端で自動停止 → 「おしまい！」と「もういちど」ボタン
- 実データは `docs/STAGE_SCHEMA.md` 末尾（実装時に `src/stages/0-0.json` へ置く）

## 8. CI・配信・ブランチ運用

- `.github/workflows/ci.yml`: すべての push と PR で `npm ci` → `npm run build` → `npm run smoke`。スクショは Actions のアーティファクトに保存。`main` への push ではさらに GitHub Pages にデプロイ
- 公開 URL: `https://hassy0511.github.io/train-game/`（Vite の `base` を `/train-game/` にする）
- Pages のソースは「GitHub Actions」。ワークフローが自動で有効化を試みる。失敗した場合はリポジトリの Settings → Pages → Source を「GitHub Actions」にする必要がある（iPad の Safari でできる）
- ブランチ: `main` が Pages に出るもの。Codex は `codex/<チケット番号>-<内容>` ブランチから main へ PR。Claude Code がレビューしてマージ
- Claude Code の基盤も PR で main に入れる（**PR を作る許可がほしい**。今は `claude/kore-yonde-jzmfff` に置いてある）

## 9. スモークテスト（Playwright）

1. ビルド済みの `dist/` を preview サーバで起動し、`/?stage=0-0` を開く
2. 画面が準備完了になるのを待つ（`data-ready` 属性）
3. レバーを「ふつう」までドラッグ（実際のポインタイベント。テスト専用の裏口は作らない）
4. 5 秒待つ。走行距離が 20 m 以上進んでいること、`sensor-1 enter` がログに出ていること、コンソールにエラーがないことを検証
5. 汽笛ボタンをタップ → クールダウン表示になることを検証
6. 0 秒と 5 秒のスクショを `tests/smoke/output/` に保存

ヘッドレス Chromium はソフトウェア描画（SwiftShader）になるので遅い。タイムアウトは長めにとる。

## 11. リスク

| リスク | 対応 |
|---|---|
| iPad Safari のメモリ制限（タブが落ちる） | Phase 0 でモデルを小さく保ち、実機で確認 |
| Rapier wasm の初回ロード | 計測して 5 MB 予算内かを確認。超えるならステージ読み込みと並列化 |
| ヘッドレスでの WebGL | SwiftShader で動く前提。動かなければ WebGL 部分をスモークから切り離し、ロジックだけ検証 |
